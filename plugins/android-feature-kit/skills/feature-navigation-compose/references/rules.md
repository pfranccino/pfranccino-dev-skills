# feature-navigation-compose rules

Every normative rule of the feature-navigation-compose skill, with a stable ID. Reviews cite these IDs, and the skill's "Before finishing" checklist points to them. The Source column names the section of `SKILL.md`, or of a file in `references/`, that explains the rule. When a rule changes there, change it here too. IDs are never reused.

The skill builds and migrates navigation. A review reads this list instead of running the skill. The migration rules (NAV-25, NAV-26, NAV-31, NAV-32) allow exceptions to other rules during a migration; NAV-31 names them.

## Rules shared by every skill of the kit

These rules have the same IDs in every skill's rules file. Where a skill has no sentence for a rule, the rule is kit policy, marked as such in the Source column.

| ID | Rule | Source |
| :--- | :--- | :--- |
| KIT-01 | The skill applies even when the task arrives as a detailed plan or ticket: the plan says what to build, the skill says how the team builds it. If the plan and the skill disagree, say so and follow the plan. A review does not flag a deviation the plan required. | Introduction of every skill |
| KIT-02 | The module's existing naming, packages and conventions win over the skill's examples when they differ in style. A review does not flag a style that follows the module. | Scope of domain-layer, data-repository, feature-ui-compose and feature-navigation-compose; kit policy for data-room and data-datastore, which have no such sentence |
| KIT-03 | The module is inferred from the paths or files the user gave; ask before writing only if more than one module fits. | Scope of domain-layer, data-repository, feature-ui-compose and feature-navigation-compose; kit policy for data-room and data-datastore, which have no such sentence |
| KIT-04 | Other modules are not edited. Each change needed outside the module is reported under "Changes needed outside this module" with the module, the reason and the exact snippet, or the report says "None". | Scope and Before finishing of every skill |
| KIT-05 | The concrete names the skill's examples stand for (the project's `Either`, MVI delegate, network helper, side effect collector, design system, dispatcher qualifier, application scope) are read from the project before writing. A required piece that does not exist is asked about, never invented or copied privately into the feature. | Read before writing of every skill, generalized as kit policy |

## Navigation rules

| ID | Rule | Source |
| :--- | :--- | :--- |
| NAV-01 | Navigation 2 with type-safe routes (`navigation-compose` 2.8+). No Navigation 3 APIs (`NavDisplay`, back stack as state). The pinned Navigation, Hilt, Lifecycle and kotlinx-serialization versions are read from the version catalog and not upgraded. | Introduction |
| NAV-02 | Work only inside the given module. Other modules are read only when needed to understand a shared type, and never edited. The orchestrator (`:app`, the `NavHost` builder, a root graph) and other features are never edited, even when the change there is obvious; each needed change is reported with its exact snippet (KIT-04). | Scope: one module only |
| NAV-03 | Existing navigation the task does not touch is not refactored; a violation in it is mentioned in one line. | Scope: one module only |
| NAV-04 | Destinations are `internal`. The only public route is the graph marker: a `@Serializable data object` with no arguments and no behavior, used to enter and for `popUpTo`. Everything else is `internal`: screens, ViewModels, contracts, presentation models. | The principle; Public surface of a feature |
| NAV-05 | Configuration enters through the signature of the graph extension. | The principle |
| NAV-06 | Exits are callbacks. A feature never navigates to another feature: it never calls `navigate` with another feature's marker or extension, and never imports another feature's routes, marker or extensions. | The principle; Before finishing |
| NAV-07 | The graph extension takes `NavController`, not `NavHostController`, and uses it only for the feature's own routes. | Public surface of a feature |
| NAV-08 | `toRoute<T>()` is called once per destination and kept in a `val`. | Public surface of a feature |
| NAV-09 | `navOptions { launchSingleTop = true }` is set on navigations that a double tap could duplicate. | Public surface of a feature |
| NAV-10 | Call sites use named arguments. | Public surface of a feature |
| NAV-11 | No `deepLinks` are declared in `composable<>`. External entry goes through the deep link processor, which uses the marker or a `navigateToX()` extension. | Public surface of a feature |
| NAV-12 | A configuration value baked into `startDestination` is fixed when the graph is built; a value that can change during the flow comes from a ViewModel. | Public surface of a feature |
| NAV-13 | Public extensions exist only when needed: `fun NavController.navigateToX(args, navOptions: NavOptions? = null)` for an internal destination that must be reached from outside with arguments, and `fun NavController.setXResult(value)` for an ephemeral UI selection returning to a screen of this feature still on the stack. The route and the result key stay `internal`. | Public surface of a feature |
| NAV-14 | Exits are lambdas in the graph signature, in three kinds: `onXRequested` (the feature needs something it does not resolve), `onXCompleted(result)` (the flow finished) and `onDismiss` (left without completing). They are named by what happened inside the feature, never by where the user should go next. Lambda parameters are named when the type does not say it all. | Exit callbacks |
| NAV-15 | Callback payloads are an identifier or primitives. A callback may carry an object only if all four hold: the type is public and lives in a shared domain or model module; it is an immutable value object with no logic; the consumer needs it whole; it cannot be rebuilt from an id. | Exit callbacks |
| NAV-16 | Data moves by kind: a route argument for a new destination; the data layer for a business fact (the producer persists it, the screen on the stack observes its repository, the graph only closes the producer); `savedStateHandle` only for an ephemeral UI selection returning to a screen still on the stack, after ruling out that it is a business fact. | Getting data from one screen to another |
| NAV-17 | A `savedStateHandle` result uses an `internal const` key of the reading feature, never a string literal in two files, and carries ids or primitives only. It is written in the graph and read in the graph: read with `getStateFlow<T?>(KEY, null)` inside `composable<>`, passed to the screen as a parameter, and cleared with `savedStateHandle[KEY] = null` when the screen reports it consumed it, never with `remove(KEY)` while the flow is collected. A writer outside the module uses a `setXResult()` extension instead of the key. Two consecutive results on the same entry are tested. | Getting data from one screen to another |
| NAV-18 | One ViewModel per screen, resolved in the stateful screen. No graph- or Activity-scoped ViewModel moves data between screens, except the flow ViewModel of a multi-step flow that builds a draft: scoped to the feature's own graph marker, holding only the draft, never returning results, with each screen keeping its own ViewModel; the `composable<>` resolves it with `remember(navController, backStackEntry) { navController.getBackStackEntry(FeatureGraph) }` and hands it to the stateful screen. Ask the user only when it is unclear which screens own the draft. | Getting data from one screen to another |
| NAV-19 | Routes and `savedStateHandle` never carry secrets (PIN, password, token, OTP, full card number, CVV), domain entities or large objects; pass the id and let the ViewModel resolve it. Personal or transactional data (RUT, amount, account alias) travels only when it is the input the destination needs to operate, cannot be rebuilt from an id, and the route with arguments is not logged or sent to analytics. An amount in a route is input, not truth: the backend revalidates it. | What may travel in a route or savedStateHandle |
| NAV-20 | A custom `NavType` is only for a small immutable value object that identifies the destination, never an entity. The project's existing `NavType` for the type is reused, and another custom `NavType` in the module is followed. It is registered in the `typeMap` of every destination that uses the type through a shared `internal val` (not `private`, because the destination's ViewModel passes the same map to `toRoute<Route>(typeMap = ...)`). `serializeAsValue` escapes with `Uri.encode`, and a test navigates for real with data containing `/`, `?`, `&` and `%`. | Custom NavType (`references/custom-navtype.md`) |
| NAV-21 | Every destination has an `internal` pair. `XScreen` (stateful) resolves the ViewModel with `hiltViewModel()`, collects state with `collectAsStateWithLifecycle()` and maps side effects to callbacks; it is what `composable<>` consumes. `XScreenContent` (stateless) receives state and lambdas with `= {}` defaults, and `@Preview` and tests target it. No screen receives `NavController` or `NavBackStackEntry`, and no composable is named `XRoute`. The contract, ViewModel and composables inside each screen follow feature-ui-compose. | Screens |
| NAV-22 | `UiState`, `UiAction` and `SideEffect` are `internal`. A `SideEffect` dies in the screen: the stateful screen translates it into a call to the hoisted callback and never passes the effect to the graph. `CollectSideEffect` is the project's collector: find it before using it, and do not write a new one in the feature. | MVI connection |
| NAV-23 | No `else` branch in a `when` over an enum or sealed type. | MVI connection |
| NAV-24 | Back from a destination that is not the first of the flow pops the back stack; the first destination calls `onDismiss` for both the toolbar and the system back, without relying on `popBackStack()` returning `false`. When a destination can be first or not depending on configuration, that configuration decides. Back has one owner per level: no `BackHandler` when the host already intercepts back. `BackHandler` is used only where back must be intercepted, and `PredictiveBackHandler` where the destination needs its own back animation. | Back handling |
| NAV-25 | A migration of existing navigation covers one module per task; when the user names several, each is handled as a self-contained change with its own report. Nothing outside the module is edited, and nothing outside may stop compiling or change behavior. Only navigation moves: no redesign of UI, business logic, ViewModels or dependency injection, and no renames navigation does not require. If the module holds several independent flows and the whole is too large for one change, one flow is migrated and the report says which ones remain. The migration preserves the start destination, the back stack after each step and back behavior, or states each difference explicitly. | Migrating (`references/migration.md`) |
| NAV-26 | A migration starts with an inventory: every destination, how it is reached (start, inside, outside the module), its arguments, every place the module navigates to another module, the current back behavior and every public navigation symbol. Outside usages of those symbols are found read-only, preferably with `android studio find-usages --short <Symbol>` (adding `--context-file <file>` for common names) or the LSP find-references tool, falling back to searching imports, and the report says which method was used. | Migrating (`references/migration.md`) |
| NAV-27 | Added or changed destinations have a navigation test with `TestNavHostController` and `ComposeNavigator` covering the start destination, the arguments each destination receives and the callbacks fired when the flow exits. | Before finishing |
| NAV-28 | The final report lists every change to the feature's public contract (graph signature, marker, extensions, callback payload types), since it is a breaking change for its consumers. | Before finishing |
| NAV-29 | When unsure about an API, check `android docs search "<topic>"` when Android CLI is available instead of guessing. On Hilt 1.3 or later, `hiltViewModel` is imported from `androidx.hilt.lifecycle.viewmodel.compose`; before that, from `androidx.hilt.navigation.compose`. | Introduction |
| NAV-30 | Feature structure: `FeatureRoutes.kt` holds the public marker and an `internal sealed class` of destinations; `FeatureGraph.kt` holds the `NavGraphBuilder` extension with configuration and exit callbacks in its signature; every destination is registered with `composable<>` in the feature graph; an origin screen's `SideEffect` is connected to its callback, and that callback to `navController.navigate(...)` in the graph. A new feature reports the mounting and wiring snippet for the orchestrator. A new callback or `navigateToX()` extension changes the public contract and is reported. | Recipes |
| NAV-31 | Migration bridges and preserved data passing, allowed exceptions during a migration (to NAV-04, NAV-06, NAV-13 and the data-passing rules): a public entry point used from outside (function, route, Activity, Fragment) stays as a thin bridge to the new graph, marked `@Deprecated` with a message naming its replacement, and a public symbol with outside usages is never deleted; a public symbol with no outside usages becomes `internal` or is removed. Direct navigation to another module moves out of screens and ViewModels into an exit callback: when the module owns the host that mounts the graph, the callback is wired there to the same call as before; when the host is outside, the callback gets a temporary default that keeps the previous behavior, marked `TODO` and reported. Existing data passing that breaks the rules but still works (for example a shared ViewModel or a loose `savedStateHandle` key, against NAV-16, NAV-17, NAV-18 or any other rule) stays unless navigation cannot be migrated without changing it, and is reported as follow-up. | Migrating (`references/migration.md`) |
| NAV-32 | A migration report adds the inventory as a short table, each bridge left in place with what must happen outside the module before it can be removed, and the behavior differences or "None". The `@Deprecated` bridges and temporary `TODO` defaults are listed separately as allowed exceptions to the checklist. | Migrating (`references/migration.md`); Before finishing |
